L5.7 AI 系统事故响应与复盘

三维坐标　layer: L5（MLOps/LLMOps）｜level: Senior｜pillar: 训推框架

L5.4 教你看指标与追踪；L5.2 教你怎么发布。本章教 出事了怎么办——AI 系统的事故与传统 Web 不同：服务可能「还在 200 OK，但答案已经错了」。

学习目标​

  • 前置知识：读过 L5.2–L5.4；理解 RAG、模型 registry、灰度发布。无需 OnCall 经验。
  • 学完产出：① 能列出 AI 系统至少 5 类独有故障模式；② 能按 SEV1/2/3 判定等级并给出响应时限；③ 能执行 MTTR 五阶段（detect → triage → mitigate → resolve → learn）；④ 能写一份合格的 blameless postmortem（timeline / impact / root cause / action items / prevention）；⑤ 完成 RAG 质量骤降 tabletop 演练。
  • 阅读姿势：Postmortem 的目标不是追责，是让同类事故在统计上不可能再发生——没有 action item + DRI + due date 的复盘等于没写。

背景与现状​

传统 Web 事故AI 系统独有事故
HTTP 5xx 飙升Silent quality degradation（200 OK，答案错）
DB 连接池耗尽Embedding 与索引版本不匹配
CPU 100%Prompt injection / jailbreak 成功
缓存穿透上游 LLM API 限流导致降级模型悄悄上线
部署回滚数据漂移导致检索失效

检测难点：质量指标（faithfulness、ragas）通常 5–15 分钟滚动窗口，告警触发时用户已受害 10 分钟。

原理与架构​

2.1 SEV 分级与响应 SLA​

等级定义响应示例
SEV1核心 API 全挂 / 数据泄露 / 越狱大规模成功5 min 响应，全员 war room推理集群全 RED；PII 泄露到日志
SEV2单租户大量错误 / RAG 质量显著退化15 minfaithfulness 5min 均值 < 0.7
SEV3单模板劣化 / 个别模型 P99 超阈1 hour某 prompt 版本 regression
SEV4非用户 facing、内部工具下一工作日实验平台不可用

2.2 MTTR 拆解​

  • Detect：SLI 告警 + 用户反馈 + 合成探测（golden query set）
  • Triage：确认 blast radius、是否 SEV1、指定 Incident Commander（IC）
  • Mitigate：优先 回滚最近变更（模型 / embedding / prompt / 索引）
  • Resolve：修根因、补测试
  • Learn：48h 内 draft postmortem，7d 内 review

2.3 AI 事故止血手册（优先序）​

  1. 回滚 model registry staging/production 指针（L5.1）
  2. 回滚 embedding 模型 + 确认 index version 匹配（L2.9）
  3. 切换路由到小模型兜底或静态 FAQ（L4.3）
  4. 关闭 Tool/MCP 外呼（Agent 路径）
  5. 扩容（若是容量型 SEV，非质量型）

2.4 Postmortem 五件套​

  1. Timeline：UTC 时间线，精确到分钟
  2. Impact：影响用户数、错误率、质量分、收入估算
  3. Root Cause：5 Whys，到可行动的系统层
  4. Action Items：每条有 DRI（负责人）+ due date + 优先级
  5. Prevention：监控/门禁/自动化补洞

Blameless 原则：写「系统允许 XX 操作缺少门禁」，不写「某某手滑」。

动手实践：Tabletop 演练 — RAG 质量骤降​

场景​

RAG faithfulness 从 0.82 → 0.61（5 分钟滚动均值），用户 #42 率先反馈「回答不相关」。

你的任务​

  1. 写出 0–30 分钟 timeline（含 IC 决策）
  2. 列出 3 条 mitigate 动作（按优先级）
  3. 完成 postmortem 草稿（五件套）

参考答案（先自己做，再对照）​

Timeline 示例：

12:03 UTC  用户 #42 Slack 反馈「回答不相关」
12:05      ragas faithfulness 5min 均值 0.61，告警 InferQualityLow 触发
12:07      OnCall 确认 SEV2；开 #incident-20250627 频道；IC=@alice
12:08      查 deploy log：11:58 embedding 服务 v2.1 上线
12:09      查 index metadata：production index 仍为 embedding_v2.0 构建
12:11      Mitigate：回滚 embedding 服务至 v2.0
12:14      faithfulness 5min 均值回升至 0.80
12:25      SEV2 关闭；开启 postmortem 文档

Root Cause（5 Whys 摘要）：

  1. 质量降因检索向量空间与索引不一致
  2. 因 embedding v2.1 上线但未触发 index rebuild
  3. 因 CI/CD 缺少「embedding 变更 → 强制 index version bump」门禁
  4. 因 registry 未把 index 列为 embedding 的 downstream dependency
  5. 因架构文档未将 index 纳入 model artifact 图

Action Items 示例：

ID动作DRIDue
AI-1CI 增加 embedding/model 变更必须附带 index rebuild job@bob7d
AI-2Production index version 写入 MLflow tag index.embedding_version@carol14d
AI-3合成 golden query 每 5min 探针，faithfulness <0.75 页 OnCall@dave3d

踩坑预警​

  1. 无变更日志：故障前 30 分钟内的发布最可疑——没有 deploy log 排障时间 ×2。
  2. 指标延迟：质量告警晚于用户感知——需 canary golden set 合成探测。
  3. 责备文化：指名道姓 → 下次隐瞒 → 复发。
  4. Action items 无 DRI：= 不会被执行。

深入思考​

思考题：SEV1 与 SEV2 的核心差异是什么（不仅是响应时间）？​

展开参考答案

SEV1 需要 组织级动员：IC 有权调用任何团队、冻结全部发布、对外 Status Page 公告、法务/安全介入（泄露/越狱）。SEV2 是 服务降级但仍有 partial 功能，通常租户级或质量级，不需 CEO 链路，但需 24h 内 postmortem。

判断关键：blast radius 是否跨全体用户 + 是否存在合规/安全后果，而非单纯错误率数字。
