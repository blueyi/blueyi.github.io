L1.8 Linux cgroups、NUMA 与 IRQ 亲和

三维坐标　layer: L1（算力与编排）｜level: Senior｜pillar: 硬件架构

L1.2 讲了 NVLink/PCIe 拓扑；L1.4 提到「GPU 挂在某 NUMA node 下」。本章把操作系统层的隔离与亲和性讲透：为什么 DataLoader 和 GPU 不在同一 NUMA 会吃掉 20%+ 吞吐，以及如何用 cgroups / numactl / taskset 收口。

学习目标​

  • 前置知识：读过 L1.2（PCIe/NUMA 拓扑）、L0.6（Linux 命令行）；会用 htop / nvidia-smi。无需内核开发经验。
  • 学完产出：① 能解释 cgroups v2 如何限制 CPU/内存/IO，以及 K8s resources.limits 如何映射到 cgroup；② 能用 numactl -H 与 nvidia-smi topo -m 对照 GPU 与 CPU 的 NUMA 归属；③ 能写一条「DataLoader 进程绑 NUMA0 + GPU0 同域」的启动命令；④ 能说明 IRQ 软中断打满错误 CPU 核时，GPU 利用率虚高的成因；⑤ 亲手对比绑核前后 DataLoader 吞吐差异（CPU 即可，无需 GPU）。
  • 阅读姿势：GPU 算力不是孤岛——CPU 喂数、PCIe DMA、跨 NUMA 访存、网络 IRQ 都会决定 MFU 上限。

背景与现状​

双路 CPU + 8 GPU 的服务器是 AI 训练标配。物理上：

  • 每颗 CPU socket 是一个 NUMA node，本地内存延迟 ~80ns，跨 socket（UPI/QPI）~150ns+。
  • GPU 通过 PCIe 挂在某一 NUMA node 的 root complex 下（nvidia-smi topo -m 的 NUMA Affinity 列）。
  • PyTorch DataLoader 默认在任意 CPU 核上跑，若与 GPU 跨 NUMA，每 batch 的 H2D 拷贝都要先跨 socket 搬内存。

业界信号：Megatron-LM、DeepSpeed 文档均推荐 numactl --interleave=all 或 --membind 绑定；NVIDIA NGC 容器镜像常带 NVML NUMA affinity 提示。忽略 NUMA 是单机「MFU 莫名偏低」的头号系统原因。

原理与架构​

2.1 cgroups v2：资源隔离的 Linux 底座​

cgroup 控制器作用AI 场景
cpu限制 CPU 时间片 / 绑核防止日志 Sidecar 抢 DataLoader 核
memory硬/软内存上限防止 host OOM 拖死 GPU 训练
io磁盘/网络 IO 权重Checkpoint 写入不饿死读盘
cpuset指定可用 CPU/内存节点NUMA 亲和的核心手段

K8s 的 resources.requests/limits 最终由 container runtime 写入 cgroup。不写 limits = 与邻居进程争抢整机资源。

2.2 NUMA 亲和：GPU 与 CPU 同域​

# 查看 NUMA 拓扑
numactl -H
# 查看 GPU ↔ CPU/GPU 互联矩阵（NV# = NVLink 条数，NUMA Affinity = GPU 归属 node）
nvidia-smi topo -m

最佳实践：

  1. 训练主进程 + DataLoader worker 绑到 GPU 所在 NUMA node 的 CPU 核。
  2. 大页内存（可选）在同一 node 预分配，减少 TLB miss。
  3. 多 GPU 单机：每张卡一套 CPU 核区间，避免 8 个 DataLoader 抢同一组核。
# 示例：GPU0 在 NUMA node 0，绑核 0-15，内存只从 node0 分配
numactl --cpunodebind=0 --membind=0 python train.py --local_rank=0

2.3 IRQ 亲和与软中断​

网卡（RoCE/IB）与 NVMe 的 IRQ 默认可能落在 CPU0。若 CPU0 同时跑 DataLoader，硬中断 + 软中断（NET_RX） 会抢占用户态，表现为 GPU 等数据、利用率锯齿。

# 查看 IRQ 分布
cat /proc/interrupts | head
# 将某 IRQ 绑到专用核（需 root，生产用 irqbalance 配置文件或 tuned）
echo 2-3 > /proc/irq/123/smp_affinity_list

原则：为「网络 / 存储 IRQ」预留 1–2 核，不与训练/DataLoader 重叠。

动手实践：NUMA 绑核对比 DataLoader 吞吐​

无需 GPU，用 CPU 模拟「跨 NUMA 访存惩罚」。

# numa_dataloader_bench.py
import time, os
import torch
from torch.utils.data import DataLoader, TensorDataset

N = 100_000
D = 4096
data = TensorDataset(torch.randn(N, D))
loader = DataLoader(data, batch_size=256, num_workers=4, pin_memory=False)

def bench():
    t0 = time.perf_counter()
    for i, (x,) in enumerate(loader):
        if i >= 200:
            break
        _ = x.sum()
    return time.perf_counter() - t0

print(f"pid={os.getpid()} elapsed={bench():.3f}s")
# 基线：不绑核
python numa_dataloader_bench.py

# 绑到 node0（双路机上对比 node1 通常更慢）
numactl --cpunodebind=0 --membind=0 python numa_dataloader_bench.py
numactl --cpunodebind=1 --membind=1 python numa_dataloader_bench.py

预期：双路服务器上，错误 node 比正确 node 慢 10–30%（视内存带宽与 worker 数而定）。单路机差异较小。

踩坑预警​

  1. --membind 与 --interleave=all 混用：interleave 适合多 GPU 均分读盘；单卡训练应 membind 到 GPU 同域。
  2. K8s 未设 CPU manager static policy：容器内看到的 CPU 列表可能是整机，绑核需配合 CPU Manager 或 guaranteed QoS。
  3. num_workers 过大：超过物理核数反而因上下文切换变慢；经验值 4–8 起步按 profiling 调整。
  4. pin_memory=True 但 CPU 不对域：pinned memory 仍在错误 NUMA 分配，H2D 收益打折。

配套代码：ai-infra-labs numa_dataloader_bench.py

深入思考​

思考题：K8s 拓扑感知调度（L1.4）与 OS 层 NUMA 绑核的关系？​

展开参考答案

K8s 调度决定 Pod 落在哪台物理机、哪张 GPU；OS 层 numactl/cpuset 决定 Pod 内部哪些 CPU/内存 node 服务这张 GPU。

二者缺一不可：调度器把 8 卡 Job 塞进同一台 NVLink 全连接机器（拓扑感知），但若容器内 DataLoader 仍跨 NUMA 喂 0 号 GPU，单机 MFU 照样上不去。生产做法是：调度器打 topology.kubernetes.io/zone 标签 + 启动脚本读 CUDA_VISIBLE_DEVICES 与 /sys/class/nvidia/gpu*/device/numa_node 自动 numactl。
